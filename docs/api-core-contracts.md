# API-контракты ядра «Улица Радости» — проектное решение

> **Назначение.** HTTP-контракты ядра: URI, payload, ответы, ошибки, вебхуки, слои DRF.
> **Статус.** Актуальный — авторитет по HTTP-контрактам, с отклонениями реализации
> (см. блок «Статус реализации» ниже). Живая схема — `GET /api/schema/` (drf-spectacular).
> Поведение входа и покупок — в `auth-flow.md` и `checkout-flow.md`.
> **Связанные документы.** `schema.md`, `project-context.md`, `schema-audit.md`,
> `schema-refactoring.md`, `public-forms-design.md`; легаси — `api-contracts-legacy.md`.
>
> Внешние стандарты: формат ошибок — **RFC 9457 «Problem Details for HTTP APIs»**;
> идемпотентность — IETF draft **`Idempotency-Key`** + паттерн Stripe; вебхуки —
> рекомендации ЮКассы (проверка IP + перезапрос статуса).

## Статус реализации

Ядро реализовано по этому контракту: OTP-вход, чекаут абонемента и пробного
с `X-Idempotency-Key`, вебхук ЮКассы, публичная витрина, ЛК, RFC 9457.
Два осознанных отклонения:

- **Пробные занятия** (`POST /checkout/trial`) — реализованы. Запись — это
  `enrollment` с `type=TRIAL`, `trial_date` и денормализованным `activity_id`;
  лимит «1 пробное на ребёнка по кружку» держит partial-unique
  `uniq_trial_per_student_per_activity`, форму строки — `ck_billing_enrollment_type_shape`.
  Цена берётся из `catalog.Activity.price` через `SchedulePort.get_slot_trial_info`.
  Бесплатное пробное подтверждается сразу (`CONFIRMED`), платное — через тот же
  шлюз и вебхук, что абонемент. Список — `GET /api/v1/me/bookings/?kind=TRIAL`
  (вместе с событиями; `GET /api/v1/me/trials` устарела), в ленте ЛК — `kind=TRIAL`. Превышение лимита → `409 TRIAL_LIMIT_EXCEEDED`.
  Пробное в группу, где ребёнок уже на абонементе → `409 STUDENT_ALREADY_ENROLLED`.
  Абонемент в группу после пробного (главный путь продажи) разрешён.
- **Оплата ивентов** (`POST /checkout/event`) — вместо онлайн-оплаты сделана гостевая
  регистрация `POST /api/v1/public/events/{id}/register/` (с обязательным
  `pd_consent: true`, `personal-data.md`). Бесплатное событие → сразу `CONFIRMED`;
  платное → `PENDING_PAYMENT`, оплата на месте. Онлайн-оплаты ивентов через ЮКассу
  пока нет (отдельная задача).
  - О каждой платной брони менеджерам уходит сообщение в Telegram (после коммита,
    задача `notify_new_registration_task`): событие, дата, число мест, имена,
    телефон и email — чтобы связаться с семьёй.
  - Если менеджер не нажал в админке «Подтвердить оплату» за
    `EVENT_PENDING_PAYMENT_TTL_MINUTES` минут (env, по умолчанию 30), свипер раз в
    10 минут снимает бронь и освобождает места. Снимается **только**
    `PENDING_PAYMENT` — подтверждённую бронь свипер не трогает, даже если
    подтверждение пришлось на момент его работы.
  - Если в брони указан email, семье уходит письмо «бронь снята». При ручной отмене
    менеджером письма нет — он связывается с семьёй сам.
  - Ограничения от выкупа мест: не больше 5 мест в одной заявке (`attendees_count`
    1–5, иначе 422); одна активная запись на номер телефона в рамках события
    (повтор → 422 `VALIDATION_ERROR` с ошибкой в поле `phone`; после отмены записаться
    снова можно). В БД — частичный уникальный индекс
    `uq_event_registration_active_phone`.
- **Журнал учителя** (`/staff/*`) — реализован в админ-панели (django-unfold), а не
  как отдельное API; см. `admin.md`. Отдельные staff-эндпоинты не понадобились.

## 0. Общие соглашения (cross-cutting)

Эти правила обязательны для **всех** эндпоинтов, включая публичные формы из
`public-forms-design.md`. Единообразие — половина удобства клиента (Nuxt 4).

### 0.1. Версионирование и базовый путь
`/(api)/v1/...`. Версия в URI (не в заголовке) — проще кэшировать, отлаживать
curl-ом и читать логи. Группировка по аудитории: `public/`, `auth/`, `me/`,
`checkout/`, `webhooks/`, `staff/`.

### 0.2. Заголовки

| Заголовок (запрос)         | Назначение |
| -------------------------- | ---------- |
| `Authorization: Bearer …` *(или cookie, см. 1.4)* | Сессия родителя/преподавателя |
| `X-Idempotency-Key: <uuid4>` | Обязателен для `POST /checkout/subscription` и `/checkout/trial` (Шаг 2.1) |
| `Content-Type: application/json` | Везде, кроме загрузки файлов |

| Заголовок (ответ)          | Назначение |
| -------------------------- | ---------- |
| `Content-Type: application/problem+json` | Только для ошибок (RFC 9457) |
| `Retry-After: <сек>`       | На `429`, cooldown OTP, `409 PAYMENT_IN_PROGRESS` и `503 PAYMENT_GATEWAY_UNAVAILABLE` |
| `X-Request-ID`             | На каждом ответе; его же пишем в `request_id` ошибки — для разбора с бэкендом |
| `X-RateLimit-Remaining`    | Сколько запросов осталось в окне |

**CORS.** Браузер пускает с фронта только origin из `CORS_ALLOWED_ORIGINS` (env).
Сверх стандартного набора `django-cors-headers` разрешён заголовок запроса
`X-Idempotency-Key` — без него браузер режет preflight чекаута. Заголовки ответа
`Retry-After` и `X-Request-ID` открыты для JS через `Access-Control-Expose-Headers`
(остальные нестандартные браузер от JS прячет).

### 0.3. Единый формат ошибок (RFC 9457) — на всю систему

Любая ошибка — `application/problem+json`. Базовые поля по RFC 9457 + наши расширения.
Тело собирает `apps.core.exceptions.problem_detail_exception_handler`:

```json
{
  "type": "urn:problem-type:noseatsconflict",
  "title": "NoSeatsConflict",
  "status": 409,
  "detail": "В выбранном слоте не осталось свободных мест.",
  "code": "NO_AVAILABLE_SEATS",
  "extensions": { "request_id": "8f0c…" }
}
```

Ошибка валидации (`422`):

```json
{
  "type": "urn:problem-type:validationerror",
  "title": "Validation Error",
  "status": 422,
  "detail": "Ошибка валидации входных данных.",
  "code": "VALIDATION_ERROR",
  "extensions": {
    "invalid_params": [{ "name": "email", "reason": "Введите правильный адрес электронной почты." }]
  }
}
```

- `code` — **всегда есть, на верхнем уровне**. Машинный enum из каталога ниже, не
  привязан к локали. Фронт делает `switch` именно по нему: несколько `409` отличаются
  только `code`. `type` и `title` выводятся из имени класса исключения и могут меняться
  при рефакторинге — на них не завязываться.
- Откуда берётся `code`: у своих исключений — `default_code` (или `code=` при `raise`);
  встроенные ошибки DRF/Django приводятся к каталогу (`not_found` → `NOT_FOUND`,
  `throttled` → `RATE_LIMITED` и т.д.); любая `422` — `VALIDATION_ERROR`; необработанное
  исключение — `500 INTERNAL_SERVER_ERROR`.
- `extensions` *(необязательное)* — есть, только если есть что положить:
  `request_id` (эхо заголовка `X-Request-ID`), `invalid_params[]` (поля с ошибками
  валидации, `name` — путь поля вида `items[0].date`) и данные конкретной ошибки
  (например, `active_enrollments` у `409 CHILD_HAS_ACTIVE_ENROLLMENTS`). Исключение
  кладёт их в свой атрибут `extensions`, обработчик сливает в ответ.
- Ответы, собранные вручную (например, `409 PAYMENT_IN_PROGRESS` с `Retry-After`),
  дополнительно содержат `instance` — путь запроса; `code` там тоже на верхнем уровне.

**Каталог бизнес-ошибок** (единый для ядра и форм):

| HTTP | `code`                     | Когда |
| ---- | -------------------------- | ----- |
| 400  | `MALFORMED_REQUEST`        | Битый JSON, неизвестный тип продукта |
| 401  | `AUTH_REQUIRED`            | Нет/протух токен (покупка абонемента/пробного гостем) |
| 403  | `FORBIDDEN_RESOURCE`       | Доступ к чужому ребёнку/абонементу (приватность) |
| 403  | `PROFILE_INCOMPLETE`       | Анкета не заполнена — ЛК и покупка закрыты (Сценарий 3) |
| 404  | `NOT_FOUND`                | Слот/тариф/ивент/транзакция не существует (чужой ребёнок в чекауте — `403 FORBIDDEN_RESOURCE`) |
| 409  | `NO_AVAILABLE_SEATS`       | Нет мест в слоте/ивенте |
| 409  | `TRIAL_LIMIT_EXCEEDED`     | Уже было пробное по этому кружку |
| 409  | `STUDENT_ALREADY_ENROLLED` | Ребёнок уже на абонементе в этой группе (повторный абонемент или пробное поверх него) |
| 409  | `CHILD_HAS_ACTIVE_ENROLLMENTS` | Удаление ребёнка с живыми записями; список — `extensions.active_enrollments` |
| 409  | `SUBSCRIPTION_EXPIRED`     | Абонемент просрочен (списание/возврат фишки) |
| 409  | `IDEMPOTENCY_KEY_REUSED`   | Ключ переиспользован с другим телом запроса |
| 409  | `PAYMENT_IN_PROGRESS`      | Платёж по этому ключу ещё обрабатывается (с `Retry-After`) |
| 422  | `VALIDATION_ERROR`         | Поля не прошли валидацию (формат, обязательность) |
| 429  | `RATE_LIMITED`             | Превышен троттлинг / cooldown OTP |
| 500  | `INTERNAL_SERVER_ERROR`    | Необработанное исключение (инцидент в логах) |
| 503  | `PAYMENT_GATEWAY_UNAVAILABLE` | ЮКасса не создала платёж; заказ отменён, повтор с тем же ключом безопасен (с `Retry-After`) |

Граница **422 vs 409**: `422` — данные синтаксически приняты, но семантически
невалидны (плохой email, пустой `slot_ids`); `409` — данные валидны, но
конфликтуют с текущим состоянием мира (мест нет, лимит исчерпан). Это снимает
вечный спор «какой код на бизнес-конфликт».

### 0.4. Деньги и время
Деньги — `integer` в копейках (как в `schema.md`). Время в ответах — ISO 8601 с TZ
(`2026-06-13T16:00:00+07:00`); абсолютные слоты — `day_of_week (0..6)` + `"HH:MM"`.

### 0.5. Постраничная выдача списков
Один класс на всё — `apps.core.pagination.LimitOffsetListPagination`: галерея
(`/public/gallery/`) и списки ЛК (Сценарий 3).

- Без `?limit` — весь список **корневым массивом**, как до пагинации (обратная
  совместимость: старый фронт ничего не замечает).
- `?limit=N` (опц. `&offset=M`) — конверт; `results` — те же элементы, что в массиве:

```json
{ "count": 23, "next": "https://…/?limit=10&offset=20",
  "previous": "https://…/?limit=10", "results": [ … ] }
```

- `limit` — от 1 до 60; больше 60 — молча урезается до 60 (`next` покажет, что
  есть ещё). `offset` — от 0.
- `limit=0`, отрицательные и нечисловые `limit`/`offset` → `422 VALIDATION_ERROR`,
  поле — в `extensions.invalid_params[].name`. Пустой `?limit=` = параметра нет.
- Порядок элементов всегда однозначный (есть уникальный «хвост» сортировки) —
  элемент не попадёт на две страницы, пока данные не изменились.

## Шаг 1. Контракты по сценариям

### Сценарий 1 — Беспарольная аутентификация (OTP по email)

> Поведенческая модель авторизации (режимы доступа, регистрация = первый вход,
> онбординг, удалённая теневая регистрация) — в `auth-flow.md`. Здесь только HTTP-контракт.
> Изменение схемы под OTP (`magic_tokens.code` + `attempts_count` вместо magic-link
> `token`) зафиксировано в `schema-refactoring.md`.

**Шаг A — запрос кода**

```
POST /api/v1/auth/otp/request
{ "email": "olga.e@example.com" }
```

Ответ — **всегда `202 Accepted`, независимо от того, есть ли такой email** (анти-энумерация:
нельзя по ответу понять, зарегистрирован ли адрес):

```json
{ "status": "sent", "resend_available_in": 60, "code_ttl": 300 }
```

- `resend_available_in` — cooldown в секундах: фронт рисует таймер «Отправить повторно через 0:59».
- На повторный запрос до истечения cooldown — `429` + `Retry-After`.

**Шаг B — верификация**

```
POST /api/v1/auth/otp/verify
{ "email": "olga.e@example.com", "code": "418302" }
```

Успех — `200`, выдача сессии (см. 1.4) и флаг анкеты:

```json
{ "access": "eyJ…", "refresh": "eyJ…", "profile_completed": false }
```

- `profile_completed: false` → фронт показывает анкету (`PATCH /me/profile`,
  Сценарий 3). Приходит при **каждом** входе, пока анкета не заполнена.
- `profile_completed: true` → сразу в ЛК или на страницу покупки (`redirectFrom`).

Ошибки: `422 VALIDATION_ERROR` (код не 6 цифр), `401 OTP_INVALID` (неверный/истёкший
код, несуществующий или деактивированный аккаунт — один ответ на всё), `429` после
5 неверных попыток (код мёртв, нужен новый).

**Архитектурные ответы:**

1. **Защита от флуда** (без капчи; см. также `public-forms-design.md §2.1`,
   обоснование ставок — `auth-flow.md` §3):
   - cooldown на отправку — 60 с на email (по `magic_tokens.created_at` в БД, работает всегда);
   - не более 5 запросов кода / час на email и 30 / час на IP (DRF-троттлинг
     `otp_request_email` / `otp_request_ip`; по IP мягче из-за CGNAT и Wi-Fi ресепшена);
   - не более 10 попыток ввода / мин на IP (`otp_verify_ip`);
   - не более 5 попыток ввода на один код, иначе код сжигается (`attempts_count` в таблице).
   - Вьюхи `/auth/otp/*` не принимают JWT: с токеном запрос обходил бы IP-лимит.
2. **Cooldown-таймер клиенту** — через тело (`resend_available_in`) и заголовок
   `Retry-After` на `429`. Фронт не считает сам — бэкенд авторитетен по времени.
3. **Хранение сессии — рекомендация: JWT в `HttpOnly; Secure; SameSite=Lax` cookie.**
   Обоснование под Nuxt 4 (SSR): токен в `localStorage`/`Bearer` доступен JS → крадётся
   при любой XSS. `HttpOnly` cookie недоступна JS и автоматически уходит при SSR-фетче.
   Цена — нужна CSRF-защита (двойной токен/`SameSite`). Если команда сознательно
   выбирает Bearer ради простоты и mobile-переиспользования — допустимо, но это
   осознанный размен безопасности на простоту, а не дефолт.
   Django-сессии отвергнуты: лишний серверный стейт, хуже для будущего mobile-клиента.
4. **Когда создаётся `Parent`** — *только при первом успешном `verify`*, не на
   `request` (детали — `auth-flow.md` §5). После `verify`: `profile_completed=false` →
   онбординг (анкета), `true` → кабинет (логин). Правило анкеты — `auth-flow.md` §4.1. Неподтверждённых профилей не
   существует: до verify в БД пишется лишь OTP-запись с TTL.

### Сценарий 2 — Динамическая сетка расписания

```
GET /api/v1/public/schedule?week_start=2026-06-15
```

`week_start` — понедельник запрашиваемой недели (по умолчанию текущая). Это **query-параметр,
а не часть пути**: неделя — это фильтр над одним ресурсом «расписание», а не отдельный
ресурс. Бэкенд проецирует абсолютные слоты на даты этой недели, накладывает маски и
считает места — клиент получает готовую к рендеру сетку.

**Response (200)** — плоский список, фронт раскидывает по колонкам дней:

```json
{
  "week_start": "2026-06-15",
  "week_end": "2026-06-21",
  "slots": [
    {
      "schedule_id": 106,
      "date": "2026-06-15",
      "day_of_week": 0,
      "start_time": "16:00",
      "end_time": "17:00",
      "activity": { "id": 1, "name": "Кружок мышления", "slug": "kruzhok-myshleniya" },
      "teacher": { "id": 2, "full_name": "Яков Леонидович Мордвинов" },
      "room": { "id": 3, "name": "Кабинет 2" },
      "capacity": { "max": 6, "taken": 4, "free": 2 },
      "is_rescheduled": false,
      "is_cancelled": false,
      "override": null
    },
    {
      "schedule_id": 106,
      "date": "2026-06-22",
      "start_time": "18:00", "end_time": "19:00",
      "is_rescheduled": true,
      "override": { "original_start_time": "16:00", "reason": "Перенос" }
    }
  ]
}
```

**Архитектурные ответы:**

- **Проекция слотов на даты** — бэкенд берёт `[week_start, week_end]`, для каждого
  активного слота вычисляет `date = week_start + day_of_week`. Никаких будущих дат в БД нет.
- **Маски** — на каждую дату подтягиваются активные `schedule_mask`: `CANCELLATION`
  → `is_cancelled: true` (слот остаётся в выдаче, помеченный, чтобы UI показал «отменено»);
  `RESCHEDULE` → подменяются время/день/кабинет, `is_rescheduled: true`, в `override`
  кладётся оригинал.
- **Свободные места** — `taken = активные REGULAR-записи + неистёкшие HELD-брони +
  пробные на эту неделю` (бронь до оплаты учтена, см. `schema-audit §1.1`). **Все три
  значения (`max/taken/free`) считает бэкенд** — фронт не вычитает.
- Структура **денормализована**: `activity/teacher/room` вложены прямо в слот, фронту
  не нужны доп. запросы и склейки.

#### Карточки кружков: `groups`

```
GET /api/v1/public/activities/
GET /api/v1/public/activities/{id}/
```

Список (без пагинации) и деталь отдают одну форму кружка. Подгруппы в `groups` —
только активные, в порядке «день недели → время начала». Поля карточки (`category`,
`price`, `cover_image`, `short_description`, `features`, `tags`) в примере опущены:

```json
{
  "id": 1,
  "name": "Кружок мышления",
  "slug": "kruzhok-myshleniya",
  "description": "…",
  "groups": [
    { "id": 106, "group_name": "Младшая", "age_min": 7, "age_max": 10, "max_capacity": 6 }
  ],
  "teachers": [{ "id": 2, "full_name": "…", "photo_url": "…", "position": "…" }],
  "days_of_week": [0, 3]
}
```

- **Возраст — на уровне подгруппы**, а не кружка: у одного кружка группы разных
  возрастов. `age_min`/`age_max` могут быть `null` (без ограничения).
- **Времени и свободных мест в карточке нет** — их показывает сетка
  (`GET /public/schedule`, `capacity`), где места считаются на конкретную дату.
  Дни занятий кружка — `days_of_week` (0 = понедельник).
- Ответ кэшируется на 5 минут и сбрасывается при сохранении кружка или группы.

#### Свободные занятия для пробного: `next-slots`

```
GET /api/v1/public/activities/{id}/next-slots/
```

Готовый список занятий кружка, на которые можно записаться на пробное, на две недели
вперёд. Без авторизации и без query-параметров. Из элемента фронт берёт `schedule_id`
и `date` и отправляет `POST /checkout/trial` с `trial_date = date` — контракт чекаута
не меняется.

**Response (200):**

```json
{
  "activity": { "id": 3, "name": "Шахматы" },
  "date_from": "2026-09-27",
  "date_to": "2026-10-10",
  "slots": [
    {
      "schedule_id": 14,
      "date": "2026-09-30",
      "start_time": "17:00",
      "end_time": "18:00",
      "group_name": "Младшая",
      "teacher": { "id": 2, "full_name": "Яков Леонидович Мордвинов" },
      "is_rescheduled": false
    }
  ]
}
```

- **Окно** — скользящее: `date_from` = сегодня, `date_to` = сегодня + 13 дней (не
  календарные недели). Каждый день недели попадает в окно дважды: у кружка с 5 занятиями
  в неделю — до 10 вариантов.
- **В списке только** занятия активных групп, которые не отменены маской, ещё не
  начались (граница — время начала с учётом переноса, `is_lesson_bookable`) и где есть
  свободное место на эту дату (постоянные записи + живые брони + пробные именно на эту
  дату). Перенесённое занятие — уже на новой дате и времени, `is_rescheduled: true`.
  Порядок: дата → время начала. Чекаут пробного проверяет дату тем же правилом
  (`SchedulePort.get_next_lesson_date` с моментом), поэтому на начавшееся сегодня
  занятие ответит ошибкой валидации по полю `trial_date`.
- **Числа мест нет** — как и в карточках кружков; раз занятие в списке, место есть.
  Подписи вида «СР 30.09, 17:00» фронт собирает сам из ISO-полей.
- **Ребёнка не учитывает:** запреты «уже было пробное по кружку» и «ребёнок уже на
  абонементе в этой группе» фронт получает при оплате — `409 TRIAL_LIMIT_EXCEEDED` /
  `409 STUDENT_ALREADY_ENROLLED`. Возраст группы не фильтруется.
- **Ошибки:** кружка нет или он выключен → `404 NOT_FOUND`. Свободных занятий нет →
  `200` с `"slots": []`.
- **Кэш 30 секунд** без инвалидации. Место, купленное за эти полминуты, чекаут
  перепроверит под блокировкой → `409 NO_AVAILABLE_SEATS`.
- **Реализация** — `apps.schedule.services.list_trial_slots`: вызывает
  `build_week_grid(week_start, activity_id=...)` на 2–3 недели, которые задевает окно, и
  фильтрует результат; своей логики масок и мест у ручки нет. Бюджет: 1 запрос на кружок
  + 2 на неделю, итого ≤ 7, от числа групп не зависит.
- **Известное ограничение** (FIXME в `build_week_grid`): на перенесённом занятии сетка
  считает пробные по исходной дате, а не по новой. Заполненная пробными перенесённая
  группа может попасть в список; при оплате будет `409 NO_AVAILABLE_SEATS`. Лишнего
  места не продаётся.

### Сценарий 3 — Личный кабинет (Dashboard)

**Решение: НЕ один тяжёлый запрос, а несколько независимых ресурсов.** Обоснование:

- разные части дашборда имеют разную «скорость порчи» (профиль статичен, лента занятий
  меняется ежедневно) → разный кэш;
- лента будущих занятий пагинируется и тяжела — нельзя держать профиль её заложником;
- частичная деградация: упал расчёт ленты — профиль и абонементы всё равно отрисуются.

| Ресурс | Эндпоинт | Что отдаёт |
| ------ | -------- | ---------- |
| Профиль + дети | `GET /api/v1/me/profile` | данные родителя, массив `children` (writable nested, см. Шаг 3) |
| Абонементы | `GET /api/v1/me/subscriptions` | оплаченные абонементы: действующие и история, с балансом по слотам |
| Мои записи | `GET /api/v1/me/bookings/?period=&kind=` | пробные занятия и регистрации на события одной лентой, по дате |
| Пробные (**устарела**) | `GET /api/v1/me/trials` | пробные занятия детей, новые по дате сверху; замена — `/me/bookings/?kind=TRIAL` |
| Лента занятий | `GET /api/v1/me/upcoming?weeks=4&child_id=` | агрегированная хронолента |
| Баланс депозита | `GET /api/v1/me/deposit/` | `{ "balance": <копейки> }`; нет депозита → `0` |
| История депозита | `GET /api/v1/me/deposit/entries/` | движения депозита, новые сверху |

Первый экран — 3 параллельных запроса (HTTP/2 их мультиплексирует). Это дешевле
одного монолита, который всё равно пришлось бы дробить пагинацией.

**Пагинация списков ЛК** — `/me/subscriptions`, `/me/trials`, `/me/upcoming`,
`/me/bookings/`, `/me/deposit/entries/` — по общим правилам §0.5: без `?limit`
массив, с `?limit&offset` конверт. Фильтры (`weeks`, `child_id`, `period`,
`kind`) сочетаются с пагинацией и сохраняются в `next`/`previous`. Где режется
страница:

- абонементы, пробные, депозит — **в SQL**: `COUNT` + `LIMIT/OFFSET`, связи
  (слоты, записи, транзакции) догружаются только для строк страницы. Число
  запросов не зависит от размера страницы (абонементы — 4, пробные — 3);
- лента — **в Python**: будущих занятий нет в БД, они генерируются на горизонт
  ≤ 8 недель (десятки строк), затем режется готовый список;
- мои записи — **в Python**: склейка двух таблиц, у родителя десятки строк
  (ниже, «Мои записи»).

**Профиль = анкета.** `GET/PATCH /api/v1/me/profile` доступен сразу после входа;
остальные ресурсы ЛК и чекаут — только после заполнения анкеты (`auth-flow.md` §4).

```json
// GET /api/v1/me/profile — родитель сразу после первого входа
{
  "id": 42, "email": "olga@example.com",
  "full_name": "", "phone": "", "referral_source": "",
  "pd_consent_at": null,
  "profile_completed": false,
  "children": []
}

// PATCH /api/v1/me/profile — заполнение анкеты (можно по частям)
{ "full_name": "Ольга Иванова", "phone": "+79131234567", "referral_source": "FRIENDS",
  "pd_consent": true }
// → 200, тот же объект профиля с "pd_consent_at": "2026-10-01T12:00:00+07:00"
//   и "profile_completed": true
```

- `pd_consent` — галочка согласия на обработку ПД (только запись). Пока
  `pd_consent_at` = `null`, анкета не заполнена. `false` → `422`: отзыв согласия — не
  через анкету. Повторное `true` ничего не меняет. Подробности — `personal-data.md`.

- `referral_source` на запись: `FRIENDS` (друзья), `SOCIAL` (соцсети), `MAPS`
  (Яндекс.Карты/2ГИС), `SEARCH` (поиск), `SIGN` (вывеска), `SCHOOL` (школа/сад),
  `OTHER`. На чтение у давних родителей бывает `UNKNOWN` («не указано»), выбрать
  его в анкете нельзя.
- Передать пустое `full_name`/`phone`/`referral_source` нельзя — `422 VALIDATION_ERROR`.
  Непереданные поля не трогаются.
- Добавлять, править и удалять детей (`POST /me/children/`, `PATCH` и `DELETE
  /me/children/{id}/`) можно до заполнения анкеты — дети часть онбординга.
- Ребёнок с такими же ФИО и датой рождения у того же родителя → `422 VALIDATION_ERROR`
  (`invalid_params[].name = "full_name"`) и при добавлении, и при переименовании.

**Удаление ребёнка — мягкое (архивация).** На ребёнка ссылаются записи, посещения и
оплаты — это учёт, стирать его нельзя. `DELETE /api/v1/me/children/{id}/` ставит
`archived_at`: ребёнок пропадает из `children` профиля, его нельзя править (`404`) и
выбрать в чекауте (`403 FORBIDDEN_RESOURCE`, как чужого). История покупок и посещений в
`/me/subscriptions`, `/me/trials` сохраняется с его именем. Того же ребёнка можно
добавить заново — это новая карточка с новым `id`. Восстановить удалённого — только
администратор в админке. `health_issues` при удалении пока не стираются.

Удалить нельзя, пока есть живая запись: абонемент (запись `HELD` или `ENROLLED`),
неоплаченная бронь пробного (`HELD`) или оплаченное пробное с датой сегодня или позже.
Прошедшее пробное и отменённые записи — история, удалению не мешают.

```json
// DELETE /api/v1/me/children/7/ → 204, без тела

// DELETE /api/v1/me/children/7/ → 409, есть живые записи
{
  "type": "urn:problem-type:childhasactiveenrollmentsconflict",
  "title": "ChildHasActiveEnrollmentsConflict",
  "status": 409,
  "detail": "У ребёнка есть действующий абонемент, неоплаченная бронь или предстоящее пробное. Удалить можно после их окончания.",
  "code": "CHILD_HAS_ACTIVE_ENROLLMENTS",
  "extensions": {
    "active_enrollments": [
      { "id": 31, "type": "REGULAR", "status": "ENROLLED",
        "activity_name": "Робототехника", "group_name": "Группа А",
        "subscription_id": 12, "trial_date": null },
      { "id": 40, "type": "TRIAL", "status": "ENROLLED",
        "activity_name": "Английский язык", "group_name": "",
        "subscription_id": null, "trial_date": "2026-10-03" }
    ]
  }
}
```

Чужой, несуществующий или уже удалённый ребёнок → `404 NOT_FOUND` (неотличимы).
Гонка «удаление против покупки» закрыта локом строки ребёнка (`FOR NO KEY UPDATE`) и в
удалении, и в чекауте: одна операция дожидается другой.

**Закрытая ручка до анкеты** — `/me/subscriptions`, `/me/trials`, `/me/upcoming`,
`/me/bookings/`, `/me/deposit/`, `/me/deposit/entries/`, `POST /checkout/subscription`,
`POST /checkout/trial`:

```json
// 403
{
  "type": "urn:problem-type:profileincomplete",
  "title": "ProfileIncomplete",
  "status": 403,
  "detail": "Заполните анкету: ФИО, телефон, «откуда вы о нас узнали» и согласие на обработку персональных данных."
}
```

Машинный признак сейчас — `type` (обработчик ошибок строит его из имени класса
исключения `ProfileIncomplete`). Когда в обработчик вернётся поле `code` (§0.3),
здесь появится `"code": "PROFILE_INCOMPLETE"` без изменений в ручках. Клиенту
проверять оба: `code === "PROFILE_INCOMPLETE" || type === "urn:problem-type:profileincomplete"`.
Без токена эти ручки отвечают `401`, как и раньше.

**Абонементы: действующие и история.** В списке только оплаченные абонементы —
`ACTIVE` и `EXPIRED` (в эти статусы абонемент попадает лишь после оплаты).
Незавершённые и брошенные оплаты (`PENDING`, `CANCELED`) не показываются. Порядок:
действующие сверху, внутри группы — новые сверху.

- **Действующий** (`ACTIVE`) — куда ребёнок ходит сейчас: слоты по живым записям,
  `remaining_sessions` — остаток фишек.
- **Истёкший** (`EXPIRED`) — что было куплено: все слоты покупки с кружком,
  группой и временем, имя ребёнка сохраняется (и после удаления ребёнка из
  профиля). `remaining_sessions` и `total_remaining` = `0`: неиспользованный
  остаток при истечении переведён деньгами на депозит (строка
  `SUBSCRIPTION_EXPIRY_CREDIT` в `/me/deposit/entries/`). `total_sessions` —
  сколько занятий было куплено.

```json
// GET /api/v1/me/subscriptions/?limit=2
{
  "count": 3, "next": "https://…/api/v1/me/subscriptions/?limit=2&offset=2",
  "previous": null,
  "results": [
    { "id": 58, "display_id": "#SUB-58", "status": "ACTIVE",
      "student_name": "Иванов Иван", "purchase_price": 400000,
      "created_at": "2026-09-20T14:03:11+03:00", "start_date": "2026-09-22",
      "expires_at": "2026-10-22T23:59:59+03:00", "total_remaining": 3,
      "slots": [ { "schedule_id": 12, "activity_name": "Шахматы",
                   "group_name": "Младшая", "schedule": "СБ 16:00-17:00",
                   "remaining_sessions": 3, "total_sessions": 4 } ] },
    { "id": 41, "display_id": "#SUB-41", "status": "EXPIRED",
      "student_name": "Иванов Иван", "purchase_price": 400000,
      "created_at": "2026-08-01T10:00:00+03:00", "start_date": "2026-08-02",
      "expires_at": "2026-09-01T23:59:59+03:00", "total_remaining": 0,
      "slots": [ { "schedule_id": 12, "activity_name": "Шахматы",
                   "group_name": "Младшая", "schedule": "СБ 16:00-17:00",
                   "remaining_sessions": 0, "total_sessions": 4 } ] }
  ]
}
```

**Лента `upcoming`** объединяет разнородные источники в один отсортированный поток.
Ключ — **дискриминатор `kind`**, чтобы фронт рендерил единым списком:

```json
// GET /api/v1/me/upcoming/?weeks=4&limit=3
{
  "count": 9, "next": "https://…/api/v1/me/upcoming/?limit=3&offset=3&weeks=4",
  "previous": null,
  "results": [
    { "kind": "SUBSCRIPTION_SESSION", "date": "15.06.2026", "time": "16:00-17:00",
      "student_id": 101, "student_name": "Иванов Иван Иванович",
      "activity_name": "Кружок мышления", "group_name": "Общая", "title": null,
      "source_type": "subscription", "source_id": 501, "is_rescheduled": false },
    { "kind": "TRIAL", "date": "17.06.2026", "time": "17:30-18:30",
      "student_id": 101, "student_name": "Иванов Иван Иванович",
      "activity_name": "Английский язык", "group_name": "Начинающие", "title": null,
      "source_type": "trial", "source_id": 45, "is_rescheduled": false },
    { "kind": "EVENT", "date": "20.06.2026", "time": "11:00-12:30",
      "student_id": null, "student_name": "Иван",
      "activity_name": null, "group_name": null, "title": "Театральные игры",
      "source_type": "event", "source_id": 5, "is_rescheduled": false }
  ]
}
```

- **Регулярные занятия по абонементу не лежат в БД** — бэкенд генерирует их из слотов
  на горизонт `weeks` (по умолчанию 4, максимум 8; как в Сценарии 2), вплетает
  пробные/ивенты и сортирует по дате и времени.
- **Offset-пагинация, как у остальных списков ЛК.** Курсор, задуманный раньше, не
  нужен: лента короткая (горизонт ≤ 8 недель) и каждый раз собирается заново.
  Порядок однозначный — при равных дате и времени дальше по `kind`, `student_id`,
  `source_id`, поэтому занятия двух детей в одну минуту не меняются местами между
  страницами. Ограничение: лента привязана к «сегодня» — если листать её в
  полночь, прошедший день уйдёт и страницы сдвинутся на его занятия.
- **Без избыточности**: профиль ребёнка в ленте — только `student_id` + имя, полная
  карточка живёт в `/me/profile`. Один источник правды на сущность.
- **События в ленте** — регистрации родителя (`parent` = он) и гостевые регистрации
  (сделанные без входа) с его email. По телефону не подтягиваются: телефон в анкете
  не подтверждается, вписав чужой номер, можно было увидеть чужих детей. Правило
  общее с «Мои записи» (`parent_event_registrations`).

**Мои записи** — `GET /api/v1/me/bookings/` — пробные занятия и регистрации на
события одним списком карточек. В БД это две разные таблицы (`enrollment` с
`type=TRIAL` и `event_registration`); они не объединяются — ручка читает обе,
приводит к одной карточке, сортирует по дате и режет страницу.

| Параметр | Значения | По умолчанию |
| -------- | -------- | ------------ |
| `period` | `upcoming` — дата ≥ сегодня; `past` — дата < сегодня; `all` | `upcoming` |
| `kind` | `TRIAL`, `EVENT` | оба |
| `limit`, `offset` | §0.5 | весь список массивом |

Другое значение `period`/`kind` → `422 VALIDATION_ERROR`; пустое = параметра нет.

```json
// GET /api/v1/me/bookings/?period=upcoming&limit=2
{
  "count": 5,
  "next": "https://…/api/v1/me/bookings/?limit=2&offset=2&period=upcoming",
  "previous": null,
  "results": [
    { "kind": "TRIAL", "id": 45, "title": "Английский язык", "group_name": "Начинающие",
      "date": "2026-10-03", "start_time": "17:30", "end_time": "18:30",
      "cost": 50000, "child_name": "Иванов Иван", "student_id": 101,
      "attendees_count": null, "status": "CONFIRMED", "status_display": "Записан",
      "is_past": false, "activity_id": 7, "event_id": null },
    { "kind": "EVENT", "id": 312, "title": "Театральные игры", "group_name": null,
      "date": "2026-10-05", "start_time": "11:00", "end_time": "12:30",
      "cost": 120000, "child_name": "Ваня", "student_id": null,
      "attendees_count": 2, "status": "PENDING", "status_display": "Ожидает оплаты",
      "is_past": false, "activity_id": null, "event_id": 5 }
  ]
}
```

- **Ключ карточки — пара `kind` + `id`.** `id` — номер строки своей таблицы (запись
  пробного / регистрация), у пробного и события они могут совпасть.
- **Порядок.** `upcoming` — ближайшие сверху; `past` — свежие сверху; `all` — сначала
  предстоящие (ближайшие сверху), потом прошедшие (свежие сверху). При равных дате и
  времени — по `kind`, затем `id`: порядок однозначный, страницы не «прыгают».
- **«Прошло» — по дате** в местном времени центра: сегодняшнее занятие или событие
  остаётся в `upcoming` до полуночи. `is_past` — готовый флаг для фронта.
- **Время.** Пробное — дата пробного + время группы. Событие — начало
  (`start_datetime`) в местном времени, конец = начало + `duration_minutes`.
- **`cost`** в копейках. Пробное — сумма транзакции покупки (снапшот цены на момент
  оплаты; `null`, если транзакции нет — например, запись заведена вручную). Событие —
  `price × attendees_count`, бесплатное — `0`; это **текущая** цена события, не
  снапшот: цены в регистрации нет, и если менеджер поменяет цену, карточка изменится.
- **Кто записан.** Пробное — `child_name` + `student_id` (ребёнок из профиля,
  удалённый тоже — это история). Событие — `attendees_count` и `child_name` из
  заявки (ребёнок там — текст, `student_id` = `null`).
- **Статус** — общий для обоих видов; исходный показан в `status_display`:

  | `status` | Пробное | Событие | `status_display` |
  | -------- | ------- | ------- | ---------------- |
  | `PENDING` | `HELD` — бронь на время оплаты (~15 мин) | `PENDING_PAYMENT` / `NEW` | «Ожидает оплаты» / для `NEW` — «Ожидает подтверждения» |
  | `CONFIRMED` | `ENROLLED` | `CONFIRMED` | «Записан» |

  Отменённые (`CANCELED` у обоих) не показываются — это в основном брошенные оплаты.
  Прошедшее подтверждённое — `CONFIRMED` + `is_past: true`; факт посещения пробного
  (журнал) пока не отдаём.
- **Чьи записи.** Пробные — детей родителя. События — как в ленте `upcoming`: свои
  регистрации + гостевые с email родителя (email подтверждён кодом входа), не по
  телефону.
- **Цена по БД** — 3 запроса при любом объёме: пробные (JOIN ребёнка, группы,
  кружка), их транзакции (prefetch), регистрации (JOIN события). С `kind` — 2 или 1.
  Слияние в Python, а не `UNION ALL` в SQL: у родителя десятки таких записей (пробное —
  одно на ребёнка на кружок), а форма даты в таблицах разная. Если записей станет
  много, переход на `UNION` — внутреннее дело бэкенда: конверт и порядок не
  изменятся.
- **Известное ограничение — переносы.** Время пробного — штатное время группы:
  маски расписания (отмена/перенос конкретного занятия) не учитываются, как и в
  `/me/trials` и `/me/upcoming`. Лечится общей функцией «занятие группы на дату»
  (отдельная задача).
- **Поиск гостевых по email** — `UPPER(email)` без индекса, т.е. просмотр таблицы
  регистраций. Для тысяч строк незаметно; при росте — функциональный индекс
  (миграция, отдельным решением).

**`GET /me/trials` устарела.** Работает как раньше (в Swagger помечена `deprecated`),
пока фронт не перейдёт на `/me/bookings/?kind=TRIAL`; после этого удаляем. Отличия
замены: общие `status` вместо `HELD/ENROLLED`, `title` вместо `activity_name`,
`child_name` вместо `student_name`, по умолчанию только предстоящие (`period=all` —
все), порядок по возрастанию даты.

**Депозит** («несгораемый остаток») — внутренний кошелёк родителя: сюда приходит
остаток истёкшего абонемента, отсюда оплачивается новый (`use_deposit` в
`POST /checkout/subscription`). Две ручки, а не одна и не поле в профиле:

- баланс нужен экрану чекаута (показать ли галочку «оплатить с депозита») — ему
  незачем тянуть историю или профиль с детьми; `GET /me/deposit/` — 1 SQL-запрос;
- профиль — редактируемый ресурс пользователя, а баланс — данные биллинга с другой
  «скоростью порчи» (меняется от каждой покупки); не смешиваем;
- история — корневой массив без `?limit` и конверт с `?limit` (§0.5).

```json
// GET /api/v1/me/deposit/
{ "balance": 250000 }

// GET /api/v1/me/deposit/entries/
[
  {
    "id": 12, "amount": 20000, "reason": "ORDER_CANCELED_RETURN",
    "reason_display": "Возврат: заказ не был оплачен",
    "subscription_id": 58, "subscription_display_id": "#SUB-58",
    "created_at": "2026-09-20T14:20:03+03:00"
  },
  {
    "id": 11, "amount": -20000, "reason": "CHECKOUT_SPEND",
    "reason_display": "Списание при покупке",
    "subscription_id": 58, "subscription_display_id": "#SUB-58",
    "created_at": "2026-09-20T14:03:11+03:00"
  },
  {
    "id": 9, "amount": 300000, "reason": "SUBSCRIPTION_EXPIRY_CREDIT",
    "reason_display": "Несгораемый остаток абонемента",
    "subscription_id": 41, "subscription_display_id": "#SUB-41",
    "created_at": "2026-09-01T03:00:05+03:00"
  }
]
```

- `amount` — знаковая сумма в копейках: `+` пришло, `−` потрачено. Инвариант:
  `balance` = сумма всех `amount`.
- `reason` — стабильный код для логики фронта, `reason_display` — текст для родителя.
- `subscription_id` есть у всех текущих причин: у начисления — абонемент напрямую, у
  списания и возврата — через транзакцию чекаута. Поле nullable на будущее.
- Списание при чекауте происходит **сразу**, до оплаты остатка картой (деньги
  «придерживаются» под заказ). Не оплатили за ~15 минут — приходит парное движение
  `ORDER_CANCELED_RETURN`, баланс восстанавливается.
- Строка депозита создаётся при первом начислении; чтение её не создаёт.
- Пагинация — по §0.5 (страница режется в SQL, один запрос + `COUNT`).

### Сценарий 4 — Унифицированная покупка и оплата

**Решение: НЕ полиморфный эндпоинт, а три независимых ресурса.**

```
POST /api/v1/checkout/subscription   (auth required + анкета)
POST /api/v1/checkout/trial          (auth required + анкета)
```

`POST /checkout/event` не реализован: события — гостевая регистрация
`POST /api/v1/public/events/{id}/register/` без онлайн-оплаты (см. «Статус реализации»).
Обоснование ниже написано для трёх ресурсов и остаётся в силе, когда оплата ивентов
появится.

> Режимы доступа и UX-флоу (2 шага, auth-gate, сохранение intent) — в `auth-flow.md`
> и `checkout-flow.md`. Родитель всегда берётся из токена (для пробного/абонемента) —
> в теле запроса вложенного `parent` нет. Теневая регистрация удалена.

Обоснование против единого `POST /checkout {type, payload}`:

- составы данных **кардинально разные** (абонемент: ребёнок+слоты; пробное: дата+1 слот;
  ивент: число мест) → полиморфный сериализатор выродится в дерево `if type==...`,
  которое невозможно строго типизировать и валидировать;
- **разные политики авторизации** на эндпоинт (401 для абонемента vs аноним для ивента) —
  на полиморфном это рантайм-ветвление вместо декларативного `permission_classes`;
- OpenAPI-схема и кодген клиента для раздельных ресурсов чисты, для полиморфного — «any».

Цена — небольшое дублирование «обёртки заказа», которое выносится в общий сервис
(Шаг 3). Это правильный размен: чистота контракта важнее DRY на уровне URL.

**Request — абонемент** (валидация в `serializers.py`, Шаг 3):

```json
{
  "student_id": 101,
  "plan_id": 3,
  "slot_ids": [106, 210],
  "use_deposit": false
}
```

- `plan_id` — активный тариф из `GET /public/plans/`. Тариф снят с продажи →
  `409 PLAN_UNAVAILABLE`, нет такого → `404`.
- `slot_ids` — id слотов (`schedule_id`), 1–10 штук, без повторов, порядок не важен.
  Обычный тариф: слотов ровно `slots_count`; безлимит (`is_unlimited: true`): не меньше
  `slots_count`. Иначе `422` с ошибкой в поле `slot_ids`. Тариф фронт выбирает сам из
  `GET /public/plans/` по числу слотов (`checkout-flow.md` §2).
- `use_deposit` *(необязательное, по умолчанию `false`)* — списать депозит
  (`GET /me/deposit/`) в счёт цены. Депозит покрывает часть цены (на карту — остаток)
  или всю цену — тогда заказ оформляется сразу, без ЮКассы (`CONFIRMED`).
- Ребёнок — только уже существующий свой (`student_id`); создание ребёнка в теле
  чекаута (`new_student`) не поддерживается — ребёнок добавляется через ЛК.

**Request — пробное:**

```json
{
  "student_id": 101,
  "schedule_id": 106,
  "trial_date": "2026-06-16"
}
```

`trial_date` — календарная дата занятия этого слота, на которое ещё открыта запись (не
отменено маской и не началось; берётся из `GET /public/activities/{id}/next-slots/`).
Цена — цена пробного кружка.

**Единый Response (`201 Created`)** — один формат на оба чекаута:

```json
{
  "transaction_id": "a1b2c3d4-e5f6-7890-1234-56789abcdef0",
  "status": "PENDING_PAYMENT",
  "payment_url": "https://yookassa.ru/checkout/payments/...",
  "expires_at": "2026-06-13T16:15:00+07:00"
}
```

Бесплатное пробное и абонемент, целиком оплаченный депозитом, → `payment_url: null`,
`expires_at: null`, `status: CONFIRMED`: заказ уже оформлен, ЮКассы нет.

**Ошибки чекаута** (формат — §0.3):

| HTTP | `code` | Когда |
| ---- | ------ | ----- |
| 403 | `FORBIDDEN_RESOURCE` | `student_id` — чужой или удалённый ребёнок |
| 403 | `PROFILE_INCOMPLETE` | Анкета не заполнена |
| 404 | `NOT_FOUND` | Тариф или слот не существует |
| 409 | `NO_AVAILABLE_SEATS` | В слоте (на дату пробного) нет мест |
| 409 | `STUDENT_ALREADY_ENROLLED` | Ребёнок уже записан в эту группу (повторный абонемент, пробное поверх абонемента) |
| 409 | `TRIAL_LIMIT_EXCEEDED` | Пробное по этому кружку уже было |
| 409 | `PLAN_UNAVAILABLE` | Тариф снят с продажи — перезапросить `GET /public/plans/` |
| 409 | `IDEMPOTENCY_KEY_REUSED` | Тот же `X-Idempotency-Key` с другим телом (§2.1) |
| 409 | `PAYMENT_IN_PROGRESS` | Запрос с этим ключом ещё выполняется; `Retry-After: 5` |
| 422 | `VALIDATION_ERROR` | Нет или битый `X-Idempotency-Key` (поле `X-Idempotency-Key` в `invalid_params`); число `slot_ids` не подходит тарифу; `trial_date` в прошлом или запись на это занятие закрыта |
| 503 | `PAYMENT_GATEWAY_UNAVAILABLE` | ЮКасса не создала платёж; заказ отменён, ключ освобождён — повторить **с тем же ключом** через `Retry-After: 30` |

**Архитектурные ответы:**

- **Связь заказа с шлюзом** — на checkout бэкенд: (1) одной транзакцией БД под
  блокировками слотов создаёт `transaction` сразу в `PENDING` с внутренним UUID и
  бронирует места (`enrollment.HELD`, `schema-audit §1.1`), депозит списывается здесь же;
  (2) **после коммита**, вне блокировок, вызывает `Payment.create` ЮКассы, передавая свой
  UUID в `metadata` и `Idempotence-Key: payment-<uuid>`; (3) сохраняет id платежа в
  `external_id` и отдаёт `confirmation_url`. Если ЮКасса не создала платёж — заказ
  отменяется (бронь и депозит возвращаются), ответ `503 PAYMENT_GATEWAY_UNAVAILABLE`.
- **Вебхуки** — см. Шаг 2.2 (отдельный раздел: replay, race conditions, валидация подлинности).

#### После оплаты: страница «результат оплаты»

ЮКасса возвращает родителя на `YOOKASSA_RETURN_URL` с id нашей транзакции:
`/checkout/result?tx=<transaction_id>` (параметр дописывается к настроенному адресу,
его собственные параметры сохраняются). Страница опрашивает статус:

```
GET /api/v1/checkout/transactions/{id}     (auth + анкета, как чекаут)
```

Чужая, несуществующая или битая `{id}` → `404` (чужое неотличимо от несуществующего).
Ответ — **исход для родителя**, а не сырой статус строки в БД:

```json
{
  "id": "a1b2c3d4-e5f6-7890-1234-56789abcdef0",
  "type": "SUBSCRIPTION",
  "status": "REFUND",
  "reason": "SEATS_TAKEN",
  "amount": 700000,
  "created_at": "2026-09-30T18:40:00+07:00",
  "expires_at": "2026-09-30T18:55:00+07:00",
  "order": {
    "title": "Абонемент «8 занятий»",
    "student_name": "Маша Иванова",
    "trial_date": null,
    "slots": [
      {"schedule_id": 106, "activity_name": "Шахматы", "group_name": "Младшая",
       "day_of_week": 0, "start_time": "16:00", "end_time": "17:00"}
    ]
  }
}
```

| `status` | Для родителя | Когда (по строке `transaction`) |
| -------- | ------------ | ------------------------------- |
| `PENDING` | ждём банк | `status = PENDING` и возврата нет |
| `SUCCEEDED` | оплачено и оформлено | `status = SUCCEEDED` и возврата нет |
| `CANCELED` | не оплачено | `status = CANCELED` и возврата нет: не оплатили за 15 минут, шлюз не создал платёж, банк/ЮКасса отменили |
| `REFUND` | оплачено, но не оформлено — деньги вернутся | `requires_compensation` **или** заполнен `refund_status` **или** `status = FAILED`. Проверяется первым: в БД такая строка бывает и `SUCCEEDED` (место ушло после оплаты), и `CANCELED` (оплатили после снятия заказа по TTL) |

- `reason` — только у `REFUND`: `SEATS_TAKEN` (место заняли, пока платили),
  `GROUP_CLOSED` (группу убрали из расписания), `PAID_AFTER_EXPIRY` (оплата пришла
  после истечения брони или снятия заказа), `AMOUNT_MISMATCH` (пришла не та сумма),
  `NOT_FULFILLED` (прочие сбои оформления; сюда же любая будущая причина). У остальных —
  `null`: причину отказа банка адаптер ЮКассы пока не разбирает.
- `amount` — копейки, сколько прошло через карту (оно же вернётся при возврате); до
  оплаты — сколько предстоит заплатить. Часть, оплаченная с депозита, сюда не входит
  и при срыве заказа возвращается на депозит.
- `expires_at` = `created_at` + 15 минут — до какого момента держим место за
  неоплаченным заказом. Это наш TTL, не ЮКассы.
- `order` — что покупали: для пробного `title = "Пробное занятие"`, `trial_date` и один
  слот; `day_of_week` — 0 = понедельник.
- Ответ `CANCELED` не всегда окончательный: если банк подтвердил оплату уже после
  снятия заказа, позже транзакция станет `REFUND`.

**Досрочная сверка.** Если строка `PENDING`, платёж заведён в ЮКассе и с первого
опроса прошло 10 секунд, ручка ставит в очередь ту же задачу, что вебхук
(`verify_and_process_payment`), — не чаще раза в 15 секунд на транзакцию (ключ в
Redis). В самом запросе к ЮКассе не ходим. Нужна, когда вебхук опоздал или не доходит
(локальная машина). Повтор безопасен: путь вебхука работает со строкой только из
`PENDING` под `SELECT … FOR UPDATE`.

### Сценарий 5 — Журнал посещаемости и списание фишек

Преподаватель открывает журнал на дату+слот и отмечает детей.

```
GET   /api/v1/staff/journal?schedule_id=106&date=2026-06-15
PATCH /api/v1/staff/attendance/{enrollment_id}
```

`GET` отдаёт список записанных детей с текущей отметкой и остатком фишек:

```json
{
  "schedule_id": 106, "date": "2026-06-15",
  "activity_name": "Кружок мышления",
  "students": [
    {
      "enrollment_id": 88, "student": { "id": 101, "full_name": "Иванов Иван Иванович" },
      "status": "NONE",
      "subscription_slot": { "id": 777, "remaining": 3 }
    }
  ]
}
```

**Отметка — `PATCH` (частичное изменение состояния существующей записи), не `POST`:**

```
PATCH /api/v1/staff/attendance/88
X-Idempotency-Key: 7c9e...      ← обязателен
{ "status": "PRESENT", "date": "2026-06-15" }
```

Ответ `200` возвращает **новый баланс**, чтобы UI не перезапрашивал:

```json
{ "enrollment_id": 88, "status": "PRESENT", "subscription_slot": { "id": 777, "remaining": 2 } }
```

**Архитектурные ответы (транзакционность):**

- Списание/возврат — критическая секция с `SELECT … FOR UPDATE` по строке
  `subscription_slot` (детально — `schema-audit §1.3`). API лишь обёртка над сервисом.
- **`PRESENT` → списание, `ABSENT/NONE` → возврат** выполняются в одной БД-транзакции
  вместе с записью `attendance`; `CHECK(remaining >= 0)` — последний рубеж.
- **Идемпотентность двух уровней**: (1) натуральный ключ `UNIQUE(student, slot, date)`
  не даёт второй фишке списаться при дубль-отметке; (2) `X-Idempotency-Key` гасит
  сетевой ретрай того же `PATCH` (Шаг 2.1). При конкурентных запросах второй ждёт на
  `FOR UPDATE` и видит уже актуальный баланс.
- `409 SUBSCRIPTION_EXPIRED` — если на момент отметки абонемент просрочен.

## Шаг 2. Безопасность, идемпотентность, вебхуки

### 2.1. X-Idempotency-Key (checkout)

Опираемся на IETF draft `Idempotency-Key` и паттерн Stripe. Заголовок у нас
называется **`X-Idempotency-Key`** (имя из драфта не используем).

**Контракт:** клиент шлёт `X-Idempotency-Key: <uuid4>` на `POST /checkout/subscription`
и `POST /checkout/trial` (больше ключ нигде не нужен). Новый ключ — на каждую новую
покупку. Логика бэкенда:

1. Таблица `idempotency_record(key PK, request_fingerprint, response_status,
   response_body, locked_until, lock_token, created_at)`.
2. На входе — `INSERT key` под уникальным индексом:
   - **новый ключ** → ключ резервируется на 15 минут, выполняем операцию, сохраняем
     ответ, отдаём клиенту;
   - **ключ существует, тот же `request_fingerprint`** (хэш пути, id родителя и тела)
     и ответ уже сохранён → отдаём **сохранённый ответ** (`201`, то же тело), операцию
     не повторяем;
   - **тот же fingerprint, но первый запрос ещё выполняется** → `409 PAYMENT_IN_PROGRESS`
     с `Retry-After: 5`. Если резерв старше 15 минут (процесс умер), его перехватывает
     новый запрос;
   - **ключ существует, другой fingerprint** → `409 IDEMPOTENCY_KEY_REUSED` (клиент
     переиспользовал ключ для другого запроса — это его баг). Порядок `slot_ids` в
     отпечаток не входит: `[101, 102]` и `[102, 101]` — один и тот же заказ;
   - **ЮКасса не создала платёж** → заказ отменён, резерв ключа снят,
     `503 PAYMENT_GATEWAY_UNAVAILABLE`: повтор с тем же ключом — новая попытка.
3. Запись живёт 24 ч, потом чистится свипером (ретраи за пределами суток бессмысленны).

Это делает «создать платёж» безопасным к повтору: двойной клик / ретрай по таймауту не
создадут вторую транзакцию. Повторное списание фишки защищено иначе — флагом
`attendance.token_debited` (Сценарий 5), а не ключом.

### 2.2. Вебхуки ЮКассы

```
POST /api/v1/webhooks/yookassa
```

**Контракт валидации подлинности (по рекомендациям ЮКассы):**

1. **HTTPS-only** — эндпоинт принимает только по TLS (ЮКасса по HTTP не шлёт).
2. **IP-allowlist** — пропускать только из диапазонов ЮКассы
   (`185.71.76.0/27`, `185.71.77.0/27`, `77.75.153.0/25`, `77.75.154.128/25`,
   и IPv6 `2a02:5180:...`). Чужой IP → `403`, не раскрывая деталей. IP берётся по
   общему правилу «адрес, который дописал свой прокси» (`deploy.md`): голый
   `REMOTE_ADDR` за прокси — это адрес прокси, а левые адреса `X-Forwarded-For`
   подделываются.
3. **Не доверять телу уведомления.** Тело — лишь сигнал «что-то произошло с платежом X».
   Бэкенд делает **независимый перезапрос** `GET /payments/{id}` к API ЮКассы и берёт
   статус **оттуда**. Это снимает риск подделки тела и устаревших данных.
4. Ответить **`200`** при успешной постановке в обработку — иначе ЮКасса будет слать ретраи.

Ответы вебхука: событие не из списка `payment.succeeded` / `payment.canceled` /
`payment.waiting_for_capture` (например, о возврате) → `200 {"status": "ignored"}`;
битый `object.id` → `422`; задача поставлена → `200 {"status": "accepted"}`; очередь недоступна → `500` (ЮКасса
повторит). Воркер повторяет сетевые сбои ЮКассы до 5 раз; 404 платежа (поддельный
вебхук) и прочие 4xx не повторяются.

**Защита от replay / race condition** (см. также `schema-audit §1.1`):

- **Идемпотентность по платежу** — `transaction.external_id UNIQUE`; повторный вебхук
  о том же платеже не создаёт второго эффекта.
- **Атомарный переход только из `pending`** — транзакция находится по нашему UUID из
  `metadata` перезапрошенного платежа и берётся `SELECT … FOR UPDATE`; работа идёт
  только из `PENDING`, иначе — идемпотентный no-op (кроме позднего успеха, ниже).
- **Сетевые задержки / гонка с TTL** — если вебхук `succeeded` пришёл после того, как
  свипер уже снял заказ по TTL (`CANCELED`, `canceled_reason=TTL_EXPIRED`) и
  освободил бронь: заказ не восстанавливается, деньги уходят в возврат через API
  ЮКассы (`PAYMENT_SUCCEEDED_AFTER_EXPIRY` → `issue_pending_refunds`).
- **Сверка вместо слепого TTL (reconciliation)** — вебхук может не дойти совсем
  (сеть, неверный URL, allowlist за прокси). Поэтому свипер (`sweep_billing_states`,
  каждые 5 минут) не снимает заказ старше 15 минут, заведённый в ЮКассе (`external_id`
  есть), пока не спросит `GET /payments/{id}`. Ответ проводится тем же кодом, что вебхук:

  | Ответ ЮКассы | Действие |
  |---|---|
  | `succeeded` | успех как от вебхука (абонемент/пробное или компенсация) + лог `CRITICAL` «вебхук не пришёл» |
  | `canceled` | отмена как от вебхука |
  | `pending` / `waiting_for_capture` | снятие по TTL + постановка в досверку (ниже) |
  | 404 / платёж ссылается на чужую транзакцию | снятие по TTL, лог `ERROR` |
  | сеть, 5xx, 4xx, битый ответ | заказ остаётся `PENDING` до следующего тика, сверка в этом тике прекращается |

  Сетевой вызов идёт вне транзакции; запись — короткой транзакцией под `FOR UPDATE`
  с проверкой «всё ещё `pending`», поэтому одновременные вебхук и сверка (или два тика
  свипера) дают один эффект. За тик — не больше 50 запросов к ЮКассе (таймаут 5 с × 50
  укладывается в интервал крона). Если сверить не удаётся 2 часа, заказ снимается
  вслепую с логом `CRITICAL` — места не держатся бесконечно. Заказ без `external_id`
  (платёж не создан, клиент не получил ссылку) снимается без сверки.
- **Досверка снятых заказов** — родитель может оплатить по старой ссылке уже после
  снятия (оплата на 16-й минуте), а вебхук — снова не дойти. Заказ, снятый по TTL с
  заведённым платежом, получает `payment_recheck_until = снятие + 24 ч`, и свипер
  остатком бюджета тика спрашивает ЮКассу, пока платёж не станет окончательным:
  `succeeded` → поздний успех, возврат + `CRITICAL`; `canceled` / 404 → досверка
  закрыта; `pending` → спросим в следующем тике. Неоплаченный платёж ЮКасса отменяет
  сама (`cancellation_details.reason = expired_on_confirmation`; срок зависит от способа
  оплаты), так что очередь рассасывается. Не получили окончательного статуса за сутки —
  досверка закрывается с `CRITICAL` для ручной проверки в кабинете ЮКассы. Если оплату
  уже учёл вебхук (заполнен `received_amount`: возврат поставлен, выплачен или ушёл на
  ручной разбор), досверка ничего не повторяет и не поднимает тревогу.
- **HTTP-клиент** — все вызовы API ЮКассы идут через один `httpx.Client` на процесс
  (пул keep-alive соединений): сверка в 50 запросов за тик не открывает 50 TLS-соединений.
- **Сверка суммы и валюты.** Сумма из перезапроса `GET /payments/{id}` сохраняется в
  `transaction.received_amount`. Если сумма или валюта не совпали с заказом —
  транзакция `failed`, бронь снимается, депозитная часть возвращается на депозит, а
  **пришедшая сумма целиком** ставится в очередь возвратов (недоплата и переплата —
  одинаково, заказ не исполняется). Платёж не в `RUB` автоматически не
  возвращается: возврат в ЮКассе идёт в валюте платежа, а мы платежей в другой
  валюте не создаём — такая транзакция уходит на ручной разбор.
- **Сумма возврата** — всегда фактически полученная (`received_amount`), а не
  ожидаемая: ЮКасса отвергает возврат больше суммы платежа. Сумма берётся из колонки,
  поэтому повтор после сбоя шлёт тот же запрос под тем же `Idempotence-Key`.
- **Повторный вебхук** по уже учтённой оплате — no-op, в том числе после выполненного
  возврата (маркер — заполненный `received_amount`).
- **Ручной разбор.** Возвраты, отвергнутые ЮКассой, отменённые ею или не в рублях,
  видны в админке «Транзакции» (фильтр «Возврат → Нужен ручной разбор»). Менеджер
  делает возврат в кабинете ЮКассы и закрывает запись кнопкой «Возврат разобран
  вручную» — фиксируется, кто и когда. Как только возврат попадает на ручной разбор,
  менеджерам уходит сообщение в Telegram (тот же чат, что для заявок с сайта): сумма,
  причина, контакты родителя, ID платежа ЮКассы. Если к моменту отправки возврат уже
  закрыли — сообщение не отправляется.
- **Итог возврата.** ЮКасса может принять возврат в обработку (`pending`) и позже
  отменить. Периодическая задача возвратов (раз в 10 минут) опрашивает
  `GET /refunds/{id}` по незавершённым: `succeeded` — возврат выполнен, `canceled` или
  отказ API — на ручной разбор. Вебхуки о возвратах не обрабатываются: итог берётся
  из API, как и статус платежа.
- **Письмо родителю** уходит только когда возврат выполнен (`succeeded`) — сразу при
  создании или по итогам опроса: сумма, дата платежа, «срок зачисления зависит от
  банка». О постановке в очередь и ручном разборе родителю не пишем — там бывает и
  «возвращать нечего».
- **Постановка тяжёлой обработки в очередь** (Taskiq, `public-forms-design §3`) —
  вебхук-вьюха валидирует, ставит задачу и быстро отдаёт `200`; бизнес-логика идёт в воркере.

## Шаг 3. Слои DRF

### 3.1. Сериализаторы

- **Сложные бизнес-правила** — в `validate()` (межполевые) и `validate_<field>()`:
  слот активен; `free > 0`; для пробного — нет существующего пробного по этому кружку
  (`TRIAL_LIMIT_EXCEEDED`); слоты абонемента не конфликтуют по времени между собой;
  `plan.sessions_count` согласован с числом выбранных слотов (4 фишки × слоты).
- **Writable nested «родитель + дети»** (checkout гостя): один сериализатор принимает
  `parent` + `student_id|new_student`. Переопределить `create()`, обернуть в
  `transaction.atomic()`: `Parent.get_or_create(email)`, затем `Student` (новый или
  проверка принадлежности существующего этому родителю — иначе `403 FORBIDDEN_RESOURCE`),
  затем `Subscription/Enrollment/Transaction`. Всё или ничего.
- Чтение и запись — **разные сериализаторы** (`...ReadSerializer` / `...WriteSerializer`):
  на вход узкий валидируемый payload, на выход — денормализованная под рендер структура.

### 3.2. N+1: где болит и что применить (обязательно)

| Эндпоинт | Риск N+1 | Обязательная конструкция ORM |
| -------- | -------- | ---------------------------- |
| `GET /public/schedule` | `activity`, `teacher`, `room` на каждый слот; счётчик мест | `select_related("activity","teacher","room")` + `annotate(taken=Count("enrollments", filter=Q(...)))` |
| `GET /public/activities` | группы, учителя и дни недели по каждому кружку | `Prefetch("slots", queryset=Schedule.objects.filter(is_active=True).select_related("teacher__user"))` — 2 запроса, без подсчёта мест |
| `GET /me/subscriptions` | план + баланс по слотам + данные слотов | `select_related("plan","student")` + `Prefetch("slots", queryset=SubscriptionSlot.objects.select_related("schedule__activity"))` |
| `GET /me/upcoming` | маски на каждую запись | `Prefetch("slot__exceptions", queryset=…filter(date__range=…), to_attr="masks_in_range")` (см. `schema-audit §4`) |
| `GET /staff/journal` | ребёнок + баланс по каждой записи | `select_related("student","subscription_slot")` |

Правило для разработчиков: **FK → `select_related` (JOIN), обратные/M2M →
`prefetch_related` (доп. запрос), агрегаты по связям → `annotate` (а не Python-цикл).**
Любой сериализатор, который в цикле трогает `obj.related.x`, обязан иметь
соответствующий `select_related`/`Prefetch` во вьюсете. Проверять через
`assertNumQueries` в тестах списочных эндпоинтов.

### 3.3. Тонкие вьюсеты
Вьюсет: permissions → разбор/валидация (сериализатор) → вызов сервиса → сериализация
ответа. Деньги, фишки, генерация календаря, процессинг вебхуков — в `services.py`,
не во вьюхах (см. `schema-audit §3.3`).

## Шаг 4. Расширяемость контрактов

Проверка устойчивости к «капризам хозяйки» (волатильность требований из `project-context.md`).

| Будущее изменение | Ломает контракт? | Почему |
| ----------------- | ---------------- | ------ |
| Новые номиналы абонементов (другое число занятий) | **Нет** | Тариф — это строка `subscription_plan`, отдаётся данными, а не зашит в структуру JSON. Добавление номинала = новая запись, контракт неизменен. |
| Групповые скидки | **Минимально** | Цена считается на бэкенде и отдаётся готовой (`total_price`). Скидка — деталь расчёта в `services.py`; можно добавить опциональное поле `discount` в ответ, не ломая существующих клиентов (additive change). |
| Новые типы разовых услуг (SERVICE) | **Нет** | Параметры услуг — в `activity.params JSONB` (`schema-refactoring §A2`). Лента `upcoming` уже полиморфна через `kind` — новый `kind` добавляется аддитивно. |
| Новый способ оплаты | **Нет** | `transaction.metadata JSONB` поглощает специфику провайдера; контракт checkout/вебхука не меняется. |

**Принципы, обеспечивающие это:**
1. **Данные вместо структуры** — варианты (тарифы, типы) приходят строками БД, а не
   формируют разные формы ответа.
2. **Дискриминатор `kind` + общий конверт** в полиморфных лентах — новый вид события
   добавляется без изменения существующих.
3. **Только аддитивные изменения** в мажорной версии: новые **опциональные** поля можно
   добавлять; удаление/переименование/смена типа → `v2`.
4. **JSONB на периферии** (`metadata`, `params`) — поглощает нестабильную форму без
   миграций контракта.
