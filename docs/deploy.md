# Развёртывание: прокси и реальный IP клиента

> **Назначение.** Что обязано быть настроено на сервере, чтобы бэкенд видел настоящий IP
> клиента: лимиты входа и форм, капча и allowlist вебхука ЮКассы.
> **Статус.** Актуальный — авторитет по доверию к прокси и `X-Forwarded-For`.
> **Связанные документы.** Лимиты входа — `auth-flow.md` §3; вебхук —
> `api-core-contracts.md` §2.2; анти-спам форм — `public-forms-design.md`.

---

## 1. Зачем это нужно

IP клиента нужен в трёх местах:

| Где | Что будет при ошибке |
| --- | -------------------- |
| Лимиты по IP (запрос кода, ввод кода, формы, ивенты) | Подделка IP → бот обходит лимиты; «все с одного IP» → один бот блокирует вход всем |
| Капча Turnstile (`remoteip`) | Хуже скоринг |
| Allowlist вебхука ЮКассы | Подделка → чужой выдаёт себя за ЮКассу; «все с IP прокси» → **все настоящие оплаты отклоняются (403)** |

Сложность в том, что за прокси `REMOTE_ADDR` — это адрес самого прокси, а настоящий
адрес приходит в заголовке `X-Forwarded-For`. Этот заголовок клиент может прислать и сам,
с любым содержимым.

## 2. Правило

**Своему прокси доверяем, клиенту — нет.** Каждый свой прокси дописывает в **конец**
`X-Forwarded-For` адрес, от которого получил запрос. Значит, если перед Django стоит
`N` своих прокси, настоящий IP клиента — **N-й адрес с конца**. Всё левее написал клиент.

```
клиент 203.0.113.7 шлёт:      X-Forwarded-For: 1.2.3.4          ← подделка
Caddy передаёт в Django:      X-Forwarded-For: 1.2.3.4, 203.0.113.7
N = 1 → берём 1-й с конца  →  203.0.113.7                        ← настоящий
```

Если прокси вообще не пишет чужой заголовок (так тоже бывает), правило даёт тот же
результат. Реализация одна на весь проект — `apps.core.net.client_ip`. Её используют
лимиты (`ClientIPRateThrottle`), капча форм и `YookassaIPAllowlist`. Встроенные троттлы
DRF смотрят на ту же настройку `NUM_PROXIES`.

## 3. Настройка `TRUSTED_PROXY_COUNT`

| Схема | Значение |
| ----- | -------- |
| Локально, `runserver` без прокси | `0` (по умолчанию при `ENVIRONMENT=local`) |
| VPS: интернет → Caddy → gunicorn | `1` |
| Облачный балансировщик → Caddy → gunicorn | `2` (и Caddy должен доверять балансировщику, см. ниже) |

**В `staging` и `production` переменная обязательна**: без неё приложение не запустится
(`ImproperlyConfigured`). Ошибка в любую сторону опасна и незаметна:
- `1` без прокси — клиент подделывает IP через заголовок;
- `0` за прокси — все клиенты «с одного IP», вебхуки ЮКассы отклоняются.

Поэтому значение задаётся явно, а не угадывается.

**Приложение не должно быть доступно в обход прокси.** Если порт gunicorn `8000` открыт
наружу, клиент придёт напрямую, и при `N = 1` его собственный заголовок сочтётся
доверенным. В `docker-compose` прод-окружения у `backend` не должно быть `ports:`, только
внутренняя сеть. Наружу смотрит лишь Caddy (80/443).

## 4. Caddy

```
api.example.ru {
    reverse_proxy backend:8000
}
```

`reverse_proxy` сам добавляет `X-Forwarded-For` с адресом клиента. Больше ничего
настраивать не нужно.

Если перед Caddy стоит балансировщик или CDN, укажите его диапазоны в `trusted_proxies`.
Иначе Caddy не примет его заголовок, и в конце окажется адрес балансировщика:

```
{
    servers {
        trusted_proxies static 10.0.0.0/8
    }
}
```

Для nginx то же самое делает `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`.
Можно и `$remote_addr`: правило «N-й с конца» работает для обоих вариантов.

## 5. Проверка после выкладки

1. Послать с внешней машины запрос с подделкой:
   `curl -H "X-Forwarded-For: 1.2.3.4" https://api.example.ru/api/v1/auth/otp/request/ …`.
   В логах лимитов или в Redis ключ `throttle_otp_request_ip_<IP>` должен содержать
   ваш настоящий IP, а не `1.2.3.4`.
2. Провести тестовый платёж ЮКассы: вебхук должен получить `200`, а не `403`.
